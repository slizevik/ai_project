# Домашнее задание №3. Эксперименты и их трекинг

**Цель:** провести серию экспериментов на данных из ДЗ №2 так, чтобы каждый запуск был записан в трекер, его можно было воспроизвести, а выбор лучшей модели был обоснован.

**Данные:** версия CIFAR-10 (или CIFAR-100), которую вы собрали и выложили в S3 в ДЗ №2, например `processed/cifar10/v1/`.

**Трекер:** MLflow или Weights & Biases — на выбор. Большой разницы между ними для этой домашки нет, но MLflow нужно развернуть самостоятельно в контейнере.

**Среда:** unix (macOS, Linux). Работаем в том же репозитории: требования ДЗ №1 и №2 продолжают действовать — изменения только через pull request, `make check` проходит без ошибок.

## Блок 2\. Скрипт обучения

Напишите скрипт, который принимает на вход **путь к конфигу** и выполняет один запуск эксперимента.

### 2.1. Конфиг одного запуска

Конфиг (YAML или JSON) содержит всё, что нужно для запуска, например:

```yaml
experiment_name: cifar10-simple-cnn
run_name: cnn-lr0.001-bs128-seed42
seed: 42

data:
  s3_path: processed/cifar10/v1
  max_train_samples: null      # можно ограничить train для быстрых экспериментов

model:
  type: simple_cnn             # или имя архитектуры из torchvision, например resnet18
  params:
    channels: [32, 64]

train:
  epochs: 10
  batch_size: 128
  lr: 0.001
```

&nbsp;

Чтобы запустить другой эксперимент, достаточно поменять конфиг — код трогать не нужно.

### 2.2. Что делает скрипт

1. Скачивает из S3 указанную версию данных в локальную папку, если её там ещё нет.  
2. Загружает картинки и разметку и нормализует изображения по `stats.json` из той же версии данных.  
3. Обучает модель на train.  
4. После каждой эпохи считает метрики на **val**: loss, accuracy, macro-F1; в конце — время обучения.  
5. Логирует запуск в трекер.  
6. Сохраняет в S3 **лучшую модель по loss на val** (см. 2.4) — чекпоинт эпохи с минимальным val loss, а не модель после последней эпохи.  
7. В конце запуска загружает эту лучшую модель, **измеряет качество на test** (loss, accuracy, macro-F1) и логирует его в трекер.

### 2.3. Модель

Выберите один из вариантов:

- **Вариант А — своя небольшая сверточная сеть на PyTorch:** 2–3 сверточных слоя и классификатор.  
- **Вариант Б — готовая архитектура из torchvision**, например `resnet18` или `mobilenet_v3_small`, с выходным слоем на 10 классов (100 для CIFAR-100). Обучать можно с нуля или от предобученных весов.

В обоих вариантах обучение идёт на CPU за несколько эпох; loss — кросс-энтропия.

**Test нужен только для итогового замера в конце запуска.** Лучший чекпоинт и лучшая конфигурация выбираются только по val.

### 2.4. Что логируется и сохраняется

В трекер для каждого запуска записываются:

- конфиг целиком — как параметры запуска;  
- версия данных (путь в S3) и seed;  
- git-коммит, на котором выполнялся запуск;  
- метрики на val по эпохам и время обучения;  
- номер эпохи лучшего чекпоинта;  
- метрики лучшей модели на test;  
- матрица ошибок на val — как картинка или таблица.

Лучшая модель вместе с конфигом и метриками (val и test) выкладывается в S3 в папку, название которой совпадает с названием эксперимента:

```
models/<experiment_name>/<run_name>/
    model.pt
    config.yaml
    metrics.json
```

## Блок 3\. Серия экспериментов

### 3.1. Конфиг сетки и скрипт запуска

1. Опишите сетку гиперпараметров в отдельном конфиге: базовый конфиг плюс параметры, которые перебираются. Например:

   ```yaml

   base: configs/simple_cnn.yaml

   grid:

     train.lr: [0.0003, 0.001, 0.003]

     train.batch_size: [64, 128]

   ```

2. Напишите скрипт (bash или Python), который принимает конфиг сетки, строит все комбинации и для каждой запускает обучение из блока 2\.

### 3.2. Что нужно провести

1. **Baseline.** Сначала — запуск самой простой модели, например сети из одного линейного слоя поверх пикселей. С ним сравниваются все остальные.  
2. **Сетка.** Минимум 6 комбинаций гиперпараметров. Все запуски сетки — в одном эксперименте трекера, имена запусков по понятному шаблону.  
3. **Выбор — только по val.** Метрики на test уже посчитаны в каждом запуске, но в выборе конфигурации не участвуют.

### 3.3. Итоги в README

Добавьте в README раздел «Эксперименты»:

- таблицу: baseline, несколько лучших конфигураций сетки, итог для выбранной конфигурации (val и test);  
- 2–3 предложения вывода: какая конфигурация выбрана и почему;  
- для W\&B — ссылку на проект.

1. Добавьте `Dockerfile` для обучения:  
   - окружение ставится из lock-файла через uv;  
   - версия базового образа зафиксирована.  
2. Запуски обучения выполняются **в контейнере**, подключённом к той же docker-сети, что S3 и MLflow.  
3. Добавьте цели в `Makefile` (названия можно выбрать свои, но смысл должен совпадать):

   - `make experiments CONFIG=configs/grid.yaml` — запустить серию экспериментов по конфигу сетки;  
   - `make infra-down` — остановить всё.  
4. В README опишите, как поднять инфраструктуру и запустить эксперименты.

> **\+5 баллов:** каждый запуск из серии выполняется в **отдельном** контейнере.

## Подсказки

- **В образе MLflow нет драйвера PostgreSQL и boto3.** Их нужно доставить: собрать свой образ на основе официального или установить при запуске контейнера (`pip install psycopg2-binary boto3` перед `mlflow server`). Так сделано в официальном примере docker-compose в репозитории MLflow — он, кстати, тоже использует RustFS и PostgreSQL.

- **MLflow отклоняет запросы по имени сервиса.** Начиная с версии 3.5, сервер MLflow проверяет заголовок `Host` и по умолчанию пропускает только localhost и частные IP-адреса. Если контейнер с обучением обращается к `http://mlflow:5000`, запрос будет отклонён. Добавьте имя сервиса в разрешённые хосты: `MLFLOW_SERVER_ALLOWED_HOSTS=mlflow:5000,localhost:*`.

- **Артефакты через сервер MLflow.** Если запустить сервер с `--serve-artifacts` и `--artifacts-destination s3://mlflow/`, клиенты отправляют артефакты через сервер, и контейнеру с обучением не нужны ключи от S3 для работы с MLflow. Самому серверу нужны `MLFLOW_S3_ENDPOINT_URL` и ключи доступа к хранилищу.

- **Ошибки при загрузке артефактов в S3.** Если MLflow падает при сохранении артефактов с ошибками вроде `InvalidRequest`, помогут те же переменные, что в ДЗ №2: `AWS_REQUEST_CHECKSUM_CALCULATION=when_required` и `AWS_RESPONSE_CHECKSUM_VALIDATION=when_required` — на этот раз в окружении сервера MLflow.

- **W\&B без интернета.** Для отладки можно запускать с `WANDB_MODE=offline`, а потом выгрузить запуски командой `wandb sync`.

- **Конфиги.** Для YAML удобна библиотека OmegaConf: она умеет объединять базовый конфиг с изменениями. Комбинации сетки строятся через `itertools.product`.

- **Скорость.** Для перебора сетки ограничьте train через `max_train_samples` и число эпох; полную длину обучения оставьте для лучших конфигураций.

- **Предобученные веса из torchvision** обучены на ImageNet: они ждут нормализацию по статистикам ImageNet и картинки крупнее 32×32. На CIFAR они тоже работают, но выигрыш от них меньше, чем на больших изображениях. Веса скачиваются при первом запуске — чтобы контейнер не качал их каждый раз, смонтируйте кеш (`TORCH_HOME`) в volume.

- **PyTorch только для CPU.** По умолчанию на Linux ставится сборка PyTorch с CUDA весом в несколько гигабайт. Чтобы поставить CPU-сборку через uv, подключите отдельный индекс пакетов:

  ```toml

  [[tool.uv.index]]

  name = "pytorch-cpu"

  url = "https://download.pytorch.org/whl/cpu"

  explicit = true


  [tool.uv.sources]

  torch = { index = "pytorch-cpu" }

  torchvision = { index = "pytorch-cpu" }

  ```

  Ориентир: небольшая сверточная сеть за несколько эпох на CPU даёт 60–70% accuracy, а модель, которая всегда угадывает один класс, — 10%.

- **Проверьте себя.** Перед сдачей удалите volumes, пересоберите образы и пройдите весь сценарий по README с нуля.
